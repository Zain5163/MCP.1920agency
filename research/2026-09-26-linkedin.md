**No refresh product is offered on a self-serve app.** Combined with the 2-month
lifetime, a LinkedIn connection must be **reauthorised every 60 days**. There is
no code that avoids this.

## VERIFIED — from documentation

### Posting

- `POST https://api.linkedin.com/rest/posts`
- Two mandatory headers: `LinkedIn-Version` in `YYYYMM` form, and
  `X-Restli-Protocol-Version: 2.0.0`. Omitting the version gives a 426, which
  reads like a client problem rather than a missing header.
- Versions are retired after about a year — the same staleness trap as a pinned
  Graph API version.
- A created post returns **201 with an empty body**. The id is in the
  `x-restli-id` **response header**, not the payload.

### The author is a URN, and the URN carries the account type

`urn:li:person:xxx` is a personal profile; `urn:li:organization:123` is a company
page. This is why `platform_account_id` stores the whole URN — one field carrying
both identity and account type, so no account-type column was needed. Same
modelling trick as Pinterest storing a board id.

### ⚠️ `commentary` is "little text", not plain text

The single most dangerous behaviour found on any platform so far.

Reserved characters — `( ) [ ] { } @ # * _ ~ < > | \` — **must be escaped**. Left
raw they do **not** produce an error: LinkedIn drops the post body from that
character onward and **still reports success**.

So `Call us (today) on 0300…` publishes as `Call us`, with a 201 and a post id.

Handled by `escapeLittleText` in `source/packages/adapters/src/linkedin.ts`, with
four tests.

### Media is uploaded, not fetched

LinkedIn is the only platform built so far that will not collect media from a URL.
`POST /rest/images?action=initializeUpload` returns a single-use `uploadUrl` and an
image URN; the bytes are then PUT to that URL. The adapter reads from disk or
downloads first.

One image uses `content.media`; several use `content.multiImage`.

### Two products are needed, not one

| Product | Grants | Without it |
|---|---|---|
| Share on LinkedIn | `w_member_social` | Cannot post |
| Sign In with LinkedIn using OpenID Connect | `openid`, `profile`, `/v2/userinfo` | **Connect fails** — no way to learn the member id, so no person URN to author as |

The second looks like a login feature that a publishing tool does not need. It is
required.

## REPORTED — plausible, not confirmed, not acted on

- **Community Management and Sign In with OpenID Connect may not coexist on one
  app.** ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5815518/cannot-enabled-community-management-api-on-a-verif))
  If true, company-page posting needs a **second** LinkedIn app rather than
  another product on this one. Not acted on — assuming an unverified constraint is
  exactly how the Threads mistake happened.
- Community Management access [reportedly requires](https://singhamandeep.com/linkedin-community-management-api-access/)
  a registered legal entity, a verified Page, a two-tier review and a screencast.
- An escaped `#` may not render as a clickable hashtag. The spec says to escape it;
  nothing found says what it looks like afterwards. Matters for a marketing agency.

## NOT CHECKED

## Consequence to be honest about

**LinkedIn posting will go out as the owner personally, not as the 1920 Agency
page.** The adapter supports organisation URNs and will work the day access
exists. But the thing an agency actually wants is not obtainable through this app
today, and no amount of code changes that.

**Advertising API approval will not fix this.** Ads and organic company-page
posting are separate products with separate approvals.
